# Review of bleu_apps, bleu_sysinfo, bleu_display

Scope: `libs/bleu_apps.c3l`, `libs/bleu_sysinfo.c3l`, `libs/bleu_display.c3l`, with the focus areas the lead named. Read against `docs/REVIEW_CHECKLIST.md`, `ARCHITECTURE.md`, `STYLE.md`, `SERVICE_TEMPLATE.md` and `C3_GOTCHAS.md`. No library code was edited; scratch probes live outside the repo. Line numbers are the working tree as read on 2026-10-20. Note: `libs/bleu_service.c3l/src/hub.c3` has an uncommitted change from another agent (an `abandon` hook for leftover commands). It bears on SI-3 and AP-1 and is not reflected in those libraries yet.

Verdict:
1. bleu_sysinfo is not safe to ship. `Sysinfo.kill` forwards any `uint` to `kill(2)`: pid 0 signals the caller's own process group (proved: the probe's session died, including an unrelated `sleep` in the group), and pids at or above 2^31 become `kill(-n)` or `kill(-1)`.
2. bleu_display's rollback has a use-after-free on the wlr route, a shutdown path that orphans an in-flight apply, a `!!` on a platform read that aborts the process, and a default-argument trap: a zero, negative or `FOREVER` `revert_after` rolls back at once (proved). A no-op plain APPLY also leaves a revert armed (proved).
3. bleu_apps is the soundest of the three. Argv construction (no shell, no re-splitting), inotify masks, and search determinism are correct. The worker's exit path skips refusing queued launches, D-Bus activation can start an app twice (25 s synchronous call, then Exec fallback), file URIs are not encoded, and the DBUS_ACTIVATE capability reports UNSUPPORTED while the code runs it.

Counts: CRITICAL 1, HIGH 4, MEDIUM 15, LOW 15 (35 defects). Suspicions are listed separately.

## Suspicions (unproven)

* apps `poll.c3:61, 71-76`: `alloc::free(mem, last.ptr)` runs on the `?? ""` literal when `fingerprint` fails. `fingerprint` cannot fail today, so this is latent, but it would free a string literal if it ever did.
* apps `search.c3` / `service.c3:59-64`: `Ranking.release` frees `hits.ptr` from `to_aligned_array`, which for an empty result may be a null or dangling pointer. Check `alloc::free` on an empty array.
* sysinfo `win_process.c3:13-41, 96`: for every process, every sample, the Windows backend opens the process, opens its token and calls `LookupAccountSid`. That runs on the single sampler thread that also serves kills, and `LookupAccountSid` can block on a domain controller, which would delay both samples and kills.
* sysinfo `mach_read.c3:160-166`: the second `proc_listpids` call can silently truncate the list if processes start between the sizing call and the listing call.
* sysinfo `mach_read.c3:211`: `ZString` reads `pbi_comm` (16 bytes) without a bound. It is safe only because the kernel NUL-terminates it.
* sysinfo `delta.c3:80-81, 102-105`: double-to-integer casts with no range check. Bounded in practice because `elapsed` is at least the sample interval.
* display `linux_wayland.c3:161`: shutdown's revert is fire-and-forget (DI-14), so the outcome after close is unknown.
* display `linux_apply.c3:341` and the pending/revert interplay: a revert that is due while a test is in flight waits for that test (`advance` returns early), and `next_wake` then returns zero, which may spin for up to `CONFIG_TIMEOUT`. Likely short in practice; not measured.

## What is good

* apps: argv is built without a shell and field values are never re-split (bleu_xdg exec.c3 :84-105, 274-300). Unknown or misplaced field codes are refused. Refusing `%` inside quotes is documented and enforced (exec.c3:136-139).
* apps: the inotify masks and flags match the uapi values (xdg_watch.c3:15-25, checked against the inotify UAPI numbers). A watch that cannot be added is only a missed optimisation, and REFRESH still works.
* apps: search is pure and totally ordered: score descending, then catalogue index ascending (search.c3:215-231), so the same query on the same state always gives the same list.
* apps: `submit` and the request release path reference-count the operation correctly on both the success and error paths (service.c3:165-177, request.c3:72-79).
* apps: the D-Bus `Activate`, `Open` and `ActivateAction` signatures match the Desktop Entry spec (`asa{sv}`, `sava{sv}`, `a{sv}`), and the desktop-startup-id and activation-token keys are right (xdg_dbus.c3:61-88, 107-122).
* apps: zombies are reaped with `waitpid(WNOHANG)` every pass, with a one-second poll while children are outstanding (xdg_launch.c3:137-146; xdg_desktop.c3:286-301).
* sysinfo: the procfs stat parser splits the command name at the first `(` and the last `)`, and the field indexes 14, 15 and 22 match proc(5) (procfs_parse.c3:395-396, 399-410). A hostile-name test exists (procfs_parse_test.c3:151).
* sysinfo: rate and share arithmetic guards counter regressions and clamps shares (delta.c3:63-106), and processes are identified by (pid, start time) so a recycled pid never inherits history (delta.c3:112-119; procfs_processes.c3:59-62).
* sysinfo: the sampler commits counters only after every read has succeeded (procfs_sample.c3:36-44).
* sysinfo: the Windows SYSTEM_PROCESS_INFORMATION offsets match the x64 layout (win_native.c3:98-120), the walk checks the header bounds and always advances (win_process.c3:54-63), and the query loop grows its buffer (win_read.c3:17-36). The macOS proc_bsdinfo and proc_taskinfo layouts match the XNU fields, and `proc_pidinfo` results are size-checked (mach_read.c3:182-189).
* display: the CoreGraphics transaction order is correct (begin, configure, then complete or cancel; cancel on every failure), and the reconfiguration callback only posts a REFRESH (macos_cg.c3 `run_transaction`, `on_reconfigure`).
* display: the RevertGuard confirm and due semantics match the doc apart from the boundary (revert.c3:30-35): a late confirm is refused and the guard stays armed, so the rollback still happens. Layout connectivity is a correct fixpoint, and the size and count bounds are checked before the fixed arrays are used (layout.c3:67, 94-127; config.c3:35).
* display: the wlr retry rule and serial handling are correct (wayland_convert.c3:36-40; linux_wlr.c3 listeners), and config objects are destroyed on normal completion (linux_apply.c3:219-225).
* display: the Windows validate-then-apply sequence uses the SetDisplayConfig flags as recorded in win_native.c3:32-37. These were not re-fetched from the primary header in this review.
