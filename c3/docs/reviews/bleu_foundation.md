# Review of bleu_core, bleu_rt and bleu_service

Verdict: not ready as the shutdown foundation. `Hub.post` after `Hub.stop` (or on a hub that never started) aborts the process, and queued operations hang unless a service passes the new `abandon` hook, which is uncommitted and optional.
The value types, `Stream`, `Mailbox`, the poller, timers, the Unix fd and fd-passing paths and `Deadline` arithmetic hold up on every path read and in the probes below, and the stream lifecycle is correct under close.
Counts: 1 CRITICAL, 2 HIGH (both partly fixed in the uncommitted working tree), 4 MEDIUM, 13 LOW.

Scope: `libs/bleu_core.c3l/src` (all 8 files plus `equal_test.c3`), `libs/bleu_rt.c3l/src` (all POSIX, Windows, Darwin and Linux files, all tests, README), `libs/bleu_service.c3l/src/hub.c3` and `hub_test.c3`, against `docs/ARCHITECTURE.md`, `docs/STYLE.md`, `docs/C3_GOTCHAS.md` and `docs/REVIEW_CHECKLIST.md`. No library code was edited. Probes live in the scratch directory `/tmp/claude-0/-home-user-BleuKit/6687942f-5aa7-51f3-b982-28eea7444ce0/scratchpad/probes/`.

Moving target: `libs/bleu_service.c3l/src/hub.c3` is uncommitted and changed while this review ran (an `AbandonFn` hook was added, then its parameter). The first `tools/check.sh` run at 07:52 UTC failed on that half-written edit; the rerun at 07:53 UTC passed. The findings below refer to the working tree as read at 07:53 UTC (md5 `f10bd9533580b900a1293102ec4af77a`). Paths are relative to `c3/`. Severity: CRITICAL = process abort reachable in normal use; HIGH = hang or wrong result reachable in normal use; MEDIUM = wrong behaviour on a documented path or missing evidence where it matters; LOW = edge case, contract or quality.

## Suspicions (unproven)

* S1 `Worker.stop` joins with no timeout (`worker.c3:135`, `thread.join()!!`). A backend that never returns hangs `Hub.stop` forever. The doc asks backends to return soon, but nothing enforces it.
* S2 `Operation.conclude` runs the completion callback with `self` after releasing the mutex (`operation.c3:146-147`). It is safe only while the completing thread still holds a reference. The contract does not say so.
* S3 After C1 is fixed by a `running` flag, a poster that read the flag before `stop` could still lock a freed mailbox. The fix therefore needs the mailbox lifetime rule in C1, not just a flag.
* S4 Pipe-based wake-ups on macOS and the Darwin close-on-exec window are known and recorded in `bleu_rt`'s README ("Not done"). Not re-verified.
* S5 `WatchId` is a `uint` that wraps after 2^32 watches, so an old id could match a later listener (`observe.c3:195`). Not realistic in practice.

## What is good

* Stream lifecycle is correct: queued events drain after `close`, `subscribe` after `close` returns `DISCONNECTED`, the oldest event is dropped and counted under overflow, and `Reader.release` after `Stream.close` is safe (`p_stream`, all checks pass).
* `Deadline` arithmetic: `FOREVER` is unbounded, `remaining()` clamps to zero, and a 317-year timeout does not expire early (`p_obs2` case E). `timer` deadlines with `FOREVER` are at the saturated maximum, not wrapped.
* `Operation` completion is exactly-once: `succeed` and `fail` both check `state >= SUCCEEDED` under the lock, and `start` and `cancel` are idempotent.
* `Hub.stop` order is right: the worker is joined before the observable and the stream are closed, so no listener or reader can see a publish after close.
* `Mailbox` lost-wakeup discipline, growth order, partial `take_all` and refusal after close are correct and tested.
* Poller: `poll` EINTR retry uses the remaining time, timeouts round up, reserved and duplicate tags are refused, and the Windows wait sweep reports every signalled handle once.
* Wake-ups: eventfd and pipe signal coalescing and EAGAIN handling are right; the Windows manual-reset event is the correct choice for level-triggered behaviour.
* Unix fds: every acquisition is paired with a `defer` close or a release into a socket, close-on-exec is set atomically on Linux (`SOCK_CLOEXEC`, `accept4`, `MSG_CMSG_CLOEXEC`), and the receiver closes excess and failed descriptors on every error path. `take_descriptors` cannot underflow on any length the kernel produces (checked against the Linux and Darwin cmsg headers).
* `fs` reads are bounded and never sized from `stat`, as the module doc says.
* `hub_main` with `abandon` (working tree) runs inside `@foreign_entry`, so temporary memory is available to the abandon callback.
