# Review of bleu_bluetooth and bleu_secrets

Reviewed at c3 HEAD 230a58b (2026-10-20). Neither library changed after its last commit (bleu_bluetooth 89e53d0 at 06:51, bleu_secrets 67e66dd at 06:40). Shared code they depend on changed during the review: bleu_service hub.c3 (438acfb, 07:53), bleu_rt worker.c3 (4545758, 07:55), bleu_core error.c3 and operation.c3 (a4c980b and 230a58b, 08:04-08:05). Findings were re-checked against those changes. At HEAD, `libs/bleu_core.c3l/src/observe.c3:290` does not compile (`else` without braces), so every build that imports bleu_core fails until that is fixed. That file is outside this review.

Verdict:
- bleu_secrets: the crypto core is sound (modexp, HKDF, CBC and PKCS#7, DH range check, and the Secret Service interop all check out). The lifetime and wiping claims are not all true: a reproduced use-after-free when an operation outlives `Keyring.close()`, and a reproduced Linux replace bug that returns a stale secret.
- bleu_bluetooth: the BlueZ agent never answers on its own and rejects stale prompt ids, and the 46-check Linux suite passes. Completion is wrong: a bus drop reports a pairing that never happened as a success, call deadlines do not fire while the worker is idle, and a request can be accepted and never completed.
- Changes are required before relying on either library's operation results or on the secrets store. Priority: S1, S2, B1, B2, B3.

Counts: HIGH 5, MEDIUM 8, LOW 11. Line numbers refer to HEAD.

## Suspicions (unproven)

- Windows (not run): `found.blob[0:n]` (`win_ops.c3:152`) and `attribute.value[0:size]` (`entry_of`) slice pointers that may be null when the size is 0.
- `ss_ops.c3:233-234` reads `pair.items[0]` and `[1]` of a peer-supplied attribute dictionary without checking the Value kind or count. A malformed reply could trap.
- `wipe.c3:39-45` assumes the inner allocator returns 16-byte-aligned blocks. Fine for libc; not checked for other allocators.
- `std/crypto/entropy.c3` (Linux): `result != Errno.EINTR` compares a negative syscall result with the positive EINTR, so EINTR is reported as unavailable. This fails closed. It is a stdlib defect and outside this scope.
- `bluez_calls.c3`: `call_sync` on the worker can block while BlueZ waits for an agent reply that the worker cannot serve until the call times out. Not reproduced.
- `bluez_calls.c3:223-233`: what BlueZ replies to a pending Pair when its device object is removed. Not checked against a real BlueZ.
- macOS: `openConnection`, `closeConnection`, `rawRSSI`, `isConnected`, `addressString`, `deviceWithAddressString:` and `pairedDevices` match blueutil's usage (blueutil.m). Public-header status was not verified because no macOS SDK is available here.

## What is good

- Secrets modexp matches Python `pow()` on the 13 repo vectors and on 130 edge vectors: bases 0, 1, 2, 3, p-3 to p-1 and 2^1023; exponents 0, 1, 2, 2^31, 2^32, p-2, p-1, 2^1024-1 and random values. The Montgomery constants are correct, and the peer range check (2 to p-2) is exact.
- Interop with secret-service-4.0.0 (fetched from static.crates.io): the crate left-pads the shared secret to 128 bytes, uses no HKDF salt, empty info, a 16-byte OKM, minimal big-endian public keys and PKCS#7 CBC. The library matches each point.
- Volatile wipes are used for the derived key (`drop`), the padded plaintext in encrypt and decrypt, `Secret.wipe`, and the arena pages (`wipe.c3:63` is volatile in the IR; `wipe_test` passes).
- No secret appears in snapshots (State is transport and lock), events (service and account only), error text, or logs. Checked by grep.
- Reserved `bleu.` keys are refused on store, read, delete and search. Search returns attributes only; the macOS read asks for data and search does not.
- The Windows blob limit (2560 bytes) and attribute limit (64) match wincred.h, and the Win32 struct layouts are correct.
- Prompts: the wait is bounded (120 s default), cancel dismisses at once, and a dismissed prompt fails with AUTH_REQUIRED. The live hang and dismiss modes pass.
- Bluetooth: all nine Agent1 method names and signatures match BlueZ's org.bluez.Agent.rst. The agent never answers on its own; its only automatic reply is a refusal when the prompt table is full. Prompt ids come from a counter and are never reused, and stale ids are refused (INVALID_STATE). PIN length and passkey range are checked. `Cancel` closes every waiting prompt.
- rfkill is read-only. The Win32 DLL bind uses `LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`, so the working directory is not searched, and the bound signatures match `bluetoothapis.h`.
- `Bluetooth.close()` is safe with tasks still held, because tasks use the service allocator rather than the struct. In-flight calls are completed when the bus drops (`fail_pending`), so waiters are not left on that path (B1 is about which status they get).
