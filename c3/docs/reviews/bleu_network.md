# Review of bleu_network

Verdict after the fix pass: every HIGH and MEDIUM finding is fixed, and so is every LOW finding the review judged cheap. Six LOW findings are WONTFIX with a reason (D18, D19, D20, D21, D28, D29; D20 is refuted by the binding). The Linux path is covered by end-to-end tests that fail on the old code. The Windows and macOS fixes are type-checked for their targets and covered by pure tests of the decisions; they were not run.
The Windows and macOS backends type-check for all six targets but have never been run, and their main paths have defects the README does not admit: Windows connect to a saved secured network fails, Windows writes an all-user profile, and on macOS without Location authorization the connected state and disconnect are wrong and connect cannot find any network.
The README "Run" claims for Linux are largely backed by `tests/nm_scenario_test.c3`; the "Compiled" claims for Windows and macOS overstate what the code does on those paths.

Scope: `libs/bleu_network.c3l/` (src, tests, README) against `docs/ARCHITECTURE.md`, `docs/STYLE.md`, `docs/SERVICE_TEMPLATE.md`, `docs/C3_GOTCHAS.md`, and `docs/research/network.md`. No library code was edited. Runtime evidence was taken from a scratch copy of the repo (see "Tests run"). Paths are relative to `libs/bleu_network.c3l/` unless they start with `libs/` or `docs/`.

## Suspicions (unproven)

These could not be shown from code alone or need a real NetworkManager, Windows or macOS.

* S1. Real NetworkManager wrong-passphrase reason. `tests/nm_mock.py:20` says a wrong passphrase ends in FAILED(120) with NO_SECRETS(7); `tests/nm_scenario_test.c3:106-110` asserts `AUTH_REJECTED` from that. The NM reference lists NO_SECRETS = 7 but not the wrong-key mapping. If real NM re-prompts through NEED_AUTH instead, the `AUTH_REJECTED` path in `nm_read.c3:210-220` is taken on a different sequence.
* S2. `Update2` with flags `0` (`nm_command.c3:334`, used by `update_profile` and `try_autoconnect`). The NetworkManager reference documents `NM_SETTINGS_UPDATE2_FLAG_NONE = 0` as "no flags set" and `TO_DISK` as the flag that persists. If nothing persists, autoconnect changes and passphrase updates vanish on restart. The mock ignores flags, so no test distinguishes the two.
* S3. CONNECT success is decided by "device ACTIVATED after the request" (`nm_pending.c3:212-225`) and never compares the device's active connection with `p.active`, which is stored (`nm_command.c3:165`) and used only for deactivate. A later ACTIVATED from another connection could complete a failed request as success.
* S4. A parked `GetSecrets` has no timeout of its own (`nm_agent.c3:75-110`). It relies on NetworkManager cancelling it. Autoconnect prompts may accumulate if NM never cancels.
* S5. CoreWLAN delegate lifetime. Callbacks that were in flight when `setDelegate:nil` ran may call `box.post` after `Hub.stop` has freed the mailbox (`corewlan_events.c3:30-38`, `:102-110`; `corewlan.c3:158-159`; `libs/bleu_service.c3l/src/hub.c3:104-115`). Depends on CoreWLAN's guarantees, not read.
* S6. CoreWLAN security classes. `PROBE_ORDER` (`corewlan_convert.c3:86-102`) tests WPA3-Personal first. If `supportsSecurity:` reports WPA3-Personal for WPA2/WPA3 transition networks, they are classed `WPA3_SAE`, contrary to the `model.c3:44` comment that they report `WPA2_PSK`. The header text is ambiguous.
* S7. Windows default DACL of the all-user profile store (see D4). Not read.
* S8. Windows `INTERFACE_STATE_NOT_READY` as "radio off" (`wlan_api.c3:473`). Not verified.
* S9. Windows connect to the network the interface already uses completes immediately (`wlan_api.c3:419-433` checks `joined` before the new attempt begins), so a changed passphrase is reported as applied without being tried.
* S10. CoreWLAN `rssiValue` 0 is treated as a real signal (`corewlan.c3:359-370`, quality 1.0). Correct only if CoreWLAN never uses 0 for "unknown".
* S11. CoreWLAN `create` uses the default interface (`client.interface`, `corewlan.c3:50`), not a named one, on Macs with several Wi-Fi interfaces.

## What is good

* Secret agent: the `ALLOW_INTERACTION` flag is checked (`nm_agent.c3:85-88`), non-security settings are refused, prompts are deferred replies, and prompt ids are monotonic `ulong`s, so a stale answer returns `NOT_FOUND` (covered by the scenario).
* NetworkManager settings: the PSK key is left out when unknown so NM asks the agent, the open profile has no security group, and the `key-mgmt` strings match nmrs (`nm_settings.c3:47-76`).
* SSID handling: octets are kept raw everywhere; labels are produced only for valid UTF-8 without NUL (`is_utf8_text` rejects NUL), profile names fall back to hex on Windows, and a non-UTF-8 SSID is covered by a Linux scenario test.
* Pending requests complete exactly once, transitions are ordered by sequence, and `after` stops a previous attempt's terminal state from completing a new request (`nm_pending.c3:199-225`).
* sysfs: `-1`, unreadable or down-interface values become empty `Maybe`s rather than zeros (`sysfs_convert.c3`), covered by tests.
* CoreWLAN constants and selectors were checked against the objc2-core-wlan bindings (see "Tests run"). Channel-to-frequency math is right for 2.4, 5 and 6 GHz.
* Windows profile XML escapes element text (`&`, `<`, `>`, `"`, `'`) and writes the SSID as hex, so no attribute or element injection path was found; a test covers the escaping.
* `load_profiles` (`nm_profile.c3:22`) takes the caller's `tmem` and opens its own `@pool()`. This looked like the dangling-tmem pattern in C3_GOTCHAS, but `push_pool` derives a child allocator and a caller-supplied `tmem` is evaluated outside it (`/opt/c3/c3/lib/std/core/allocators.c3:40-57`, `/opt/c3/c3/lib/std/core/mem.c3:792-797`). It is safe. A probe confirmed it.
* Everything type-checks for all six targets, and the Linux suite passes.

## Resolution

Tests: `libs/bleu_network.c3l/tests/run.sh` runs 51 `bleu::network` tests (85 before this change: the other tests are the dependency libraries'), all passing. Each end-to-end regression test was run against the original library and failed there (`a_failed_read_settles_no_request`, `a_failed_sub_read_keeps_the_previous_networks`, `an_access_point_that_left_is_not_listed` (crashed the old code), `a_refused_agent_withdraws_the_prompt_capability`, `a_superseded_prompt_is_withdrawn`, `every_saved_profile_of_a_network_is_forgotten`). The pure tests of new functions cannot compile against the original library, so their failure before is by absence.

Six targets: the library type-checks for linux-x64, linux-aarch64, macos-aarch64, macos-x64, windows-x64 and windows-aarch64 against the dependencies at the commit the task started from (`4545758`): the shared tree was being changed by other agents, so `tools/check.sh` on the working tree could not be used.

Not verified on hardware: every Windows and macOS behaviour (D3 ERROR_NOT_FOUND for a missing profile, D5 field semantics, D8 notification flow, D4 default DACL). Those are type-checked and reasoned from the sources cited above.

Decisions that differ from the suggested fixes: D6 refuses (bleu does not request Location, because the request belongs to the host app's bundle); D10 uses the first publication as the handshake, so capabilities are final when `open` returns; D2 keeps the previous part and adds `stale` instead of skipping the whole picture; D24 uses SHA-256 rather than FNV; D20 is refuted by the binding.
